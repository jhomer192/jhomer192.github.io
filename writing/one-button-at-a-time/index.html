One button at a time

Local models play Pokémon without a harness doing the work
Writing · September 2026

The only thing the model is ever allowed to do is press one button. Everything else follows from that.

It is easy to make a model look like it is playing a game. Give it a fight_battle() function and a walk_to_gym() function and it will finish the game without ever making a decision. What you are testing then is the harness, not the model. I wanted to know what the model could actually do, so my Pokémon agent has a single rule: the only action it can take is press(button). No macro for a battle turn, a menu, or a route. Every step across Kanto is a press it chose.

That one constraint shaped the whole system. Here is what fell out of it.

No single model does it all

A 7B vision model is not a good strategist, and a good strategist cannot read pixels. So the loop is split. A vision-language model (qwen2.5vl:7b) turns the raw frame into a structured observation: what kind of screen this is, the dialogue on it, where the menu cursor sits, HP, move PP. A stronger text model (qwen2.5:14b or qwen3.6:27b) reads that observation and answers with one button and one sentence of reasoning.

Around those two sit specialists that see what a screenshot cannot. They read the console's own memory for the route through a map whose barriers are painted on at load time, derive the level cap implied by the next major battle from the game's trainer data, score catches and party composition, and check whether the wild encounter on screen is a 1-in-8192 shiny.

The rule for every specialist is the same: they advise, they never press. Their output arrives as text the deciding model is free to ignore. When I audited where each press came from, about 99% traced back to the deciding model; the remainder is bookkeeping the game itself leaves behind (advancing text, dismissing a repeated prompt).

Tools inform, never choose

This is the line I kept having to re-draw. It is tempting, when the model walks into the same wall twelve times, to give pathfinding the controller for a few steps. Every time I did, the run got better and the experiment got worse. The compromise that held: pathfinding, battle state, and level caps are offered as advice in the observation; move selection, switching, healing, and where to walk stay with the model.

The pleasant side effect is that nothing in the path is specific to one cartridge. The same loop drives FireRed and Emerald side by side, with three runs at once that relaunch themselves when one wedges.

Log everything, watch nothing

A run that takes days cannot be supervised by sitting in front of it. Every sentence either game prints is logged, and each run writes a trace with one record per decision: what the model was shown, what it answered, which buttons fired, and the state before and after. A browser panel streams the same thing live, but the point of the trace is that a stall gets diagnosed from the artifacts afterwards, not caught in the moment.

Where the ceiling turned out to be

Beaten so far: Brock end to end, and Elite Four Lorelei with all six of the party still standing. The failure that preceded that win was tactical: a weaker deciding model overstayed a bad matchup and lost a Pokémon it should have switched out. Swapping in a deeper model fixed it without touching the harness. That is the result I was hoping for. The ceiling is the model's depth, not the scaffolding around it.

What it runs on

Python, mGBA, and Ollama. Every agent runs on one machine on my own GPU: no API key, no cloud model, no per-token bill. Nothing leaves the desk, so the only running cost is electricity. Which is also why "one button at a time" is affordable to test at all; at API prices, a per-frame decision loop over a multi-day run would be a very different budget conversation.
