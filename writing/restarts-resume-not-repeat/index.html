Restarts resume, not repeat

What it took to keep coding agents in a Discord server
Writing · September 2026

A Discord guild already has rooms, clients on every device, and an answer to who is allowed to talk. It turns out to be a good home for a coding agent.

Claude Discord is a set of self-hostable Claude bots that live in a private Discord server. One process is one bot, with its own token, working directory, persona and conversation state, and several of them in the same guild can hand work to each other. Most of the interesting engineering was not in talking to the model. It was in the plumbing that keeps a long-lived agent from doing something dumb.

Why Discord

A guild already has rooms to separate work, clients on every device, and a built-in answer to the question of who is allowed to talk. Inside a channel the bot keeps a live Claude session rather than starting cold on each message, which is what makes a room read like a conversation instead of a queue of one-shot prompts.

Three gates before the model

Every incoming message passes three checks before a token is spent. An integrity check drops the bot's own messages, webhook-forged ones, and Discord system messages. A fail-closed allowlist refuses to start at all without a valid owner user ID. And an engagement rule decides whether the message deserves an answer: mentions everywhere, anything in a channel the bot has chosen to watch, and peer bots under a cooldown.

The bug that named the article

Early on, restarting a bot was dangerous. It would replay recent channel history to rebuild context, then treat all of it as work, and answer days-old requests instead of the message that had just tagged it. The fix is a persisted watermark: on restart, recent history is replayed and split at the watermark, so everything at or before the last reply is labelled background and only what arrived after it is treated as work. Restarts resume; they don't repeat.

Two bots left alone will talk forever

Run more than one instance in the same guild and they appear in the member list, mention each other by name, and a bot pulled into a room by a peer answers there. That is useful right up until two of them start replying to each other indefinitely. So a bot-to-bot exchange stops after six consecutive turns, pauses, and pings its owner. Any human message resets the count.

Sessions are memory, so pool them

Each channel holds its own ClaudeSDKClient. They are not free: roughly 190 MB each while warm. An LRU pool keeps three alive and tears down the least recently used one under memory pressure, with one rule that matters more than the eviction policy: never evict a session with a turn still running.

Let the bot manage its own presence

An in-process MCP server hands the model tools for Discord itself: reading any channel's history, starting and stopping watching channels (the set survives restarts), posting into another room, and creating, renaming, moving or deleting channels. It sounds like a lot of rope. In practice it is what lets you say "make a channel for the icon work and move this there" and have that be the whole instruction.

Small things that make it feel finished

Replies land in the message that announced them: a "working" placeholder is edited into the answer as it streams, split at Discord's 2,000-character limit and attached as a file past 6,000. /stop interrupts the running turn and keeps the session, so the context survives the cancel. Auth is an OAuth token from claude setup-token, so turns bill against a Claude plan rather than per-token API credit.

Python, discord.py, and the Claude Agent SDK. Each instance is a single process on a host you control.
